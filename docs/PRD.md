## 1. 제품 개요

### 1.1 한 줄 정의

VYNL은 판매자가 보유한 실물 음악 앨범을 표준화된 앨범 카탈로그에 연결해 등록하고, 구매자가 고정가로 결제한 뒤 배송 추적·구매 확정·분쟁 보호를 거쳐 거래를 완료하는 플랫폼이다.

### 1.2 MVP 결정 사항

요구사항이 모호한 부분은 다음과 같이 단순한 기본값으로 정한다. 변경 시 본 문서의 범위·상태 모델·인수 기준을 함께 갱신한다.

- 거래 대상은 LP, CD, 카세트 등 합법적으로 재판매 가능한 실물 음악 앨범이다. 디지털 음원, 티켓, 단독 포토카드 등은 제외한다.
- 서비스 지역은 대한민국, 통화는 KRW, 언어는 한국어로 한정한다.
- 개인 간 고정가 즉시 구매만 지원한다.
- 판매글 하나는 실물 한 개, 수량 1개를 의미한다.
- 판매자가 구매자에게 추적 가능한 택배로 직접 발송한다.
- 외부 PG의 결제·환불·구매안전 또는 마켓플레이스 정산 기능을 사용한다. 서비스가 카드번호나 자체 예치금을 보관하지 않는다.
- 판매대금은 구매 확정 전까지 정산 보류하고, 배송 완료 후 72시간 안에 분쟁이 없으면 자동 구매 확정한다.
- 자체 검수센터는 운영하지 않는다. 따라서 모든 화면에서 플랫폼의 실물 검수 여부와 보증 범위를 오인 없이 표시한다.
- 모바일 웹을 우선 제공하되 데스크톱에서도 핵심 흐름을 완료할 수 있어야 한다.

### 1.3 해결할 문제

구매자는 다음 문제를 겪는다.

- 같은 앨범도 매체, 발매국, 발매 연도, 카탈로그 번호, 초판·재판, 색상반 등 판본이 달라 원하는 상품을 찾기 어렵다.
- 디스크·커버 상태와 포토카드, 북클릿, 포스터 등 구성품 포함 여부가 판매자마다 다르게 표현된다.
- 외부 송금 중심의 거래는 미발송, 설명 불일치, 위조 의심, 분쟁 시 환불 위험이 크다.
- 결제 후 누가 무엇을 언제 해야 하는지 알기 어렵다.

판매자는 다음 문제를 겪는다.

- 이미 알려진 앨범 정보를 매번 다시 입력해야 한다.
- 구매 의사가 불확실한 문의와 가격 협상에 시간이 든다.
- 배송 후 구매자 미응답, 허위 분쟁, 정산 지연을 예측하기 어렵다.

운영자는 다음 문제를 겪는다.

- 주문 당시 설명과 사진, 결제·배송 이벤트가 보존되지 않으면 분쟁을 일관되게 판단하기 어렵다.
- 결제, 배송, 분쟁, 정산 상태를 한 값으로 관리하면 잘못된 환불·중복 정산이 발생하기 쉽다.

### 1.4 가치 제안

- 구매자: 정확한 판본과 실제 상태를 비교하고 원결제 수단 환불 보호가 있는 거래를 할 수 있다.
- 판매자: 공용 카탈로그를 선택해 빠르게 등록하고, 정해진 절차에 따라 예측 가능하게 정산받을 수 있다.
- 운영자: 주문 스냅샷과 상태 이력, 증빙을 한곳에서 확인해 거래 사고를 관리할 수 있다.

### 1.5 제품 원칙

1. **카탈로그 우선:** 앨범의 공통 정보와 개별 실물의 상태 정보를 분리한다.
2. **결제 전 공개:** 상태, 하자, 구성품, 전체 결제액을 결제 전에 확정한다.
3. **상태 기반 보호:** 결제, 배송, 분쟁, 정산 상태가 충족될 때만 다음 금전 처리를 허용한다.
4. **명시적인 다음 행동:** 모든 거래 화면에 현재 상태, 다음 행동 주체, 기한을 표시한다.
5. **운영 가능한 안전성:** 자동화가 불확실한 예외는 증빙과 감사 로그를 갖춘 운영자 심사로 수렴시킨다.

## 2. 목표와 성공 지표

### 2.1 제품 목표

- 사용자가 원하는 앨범과 판본을 검색하고 판매 중인 실물을 비교할 수 있다.
- 판매자가 필수 상태 정보와 실사 사진을 포함한 판매글을 등록할 수 있다.
- 한 명의 구매자만 판매글을 점유하고 결제를 완료할 수 있다.
- 결제 후 발송, 배송, 구매 확정, 정산까지 양측이 거래 상태를 추적할 수 있다.
- 설명 불일치나 배송 사고 발생 시 정산을 멈추고 증빙 기반 분쟁·환불을 처리할 수 있다.
- 운영자가 사용자, 판매글, 주문, 환불, 분쟁, 정산을 감사 가능한 방식으로 관리할 수 있다.

### 2.2 비즈니스 목표

- 앨범 거래에 필요한 정보 구조와 안전거래 흐름이 실제 수요·공급을 연결하는지 검증한다.
- 반복 가능한 거래 완료율과 분쟁 처리 비용의 기준선을 확보한다.
- 입찰, 검수, 커뮤니티 등 확장 기능을 추가하기 전에 고정가 거래의 유동성을 확인한다.

### 2.3 핵심 지표

북극성 지표는 **주간 분쟁 없는 거래 완료 건수**다.

| 구분 | 지표 | Closed Beta 초기 목표 |
| --- | --- | --- |
| 공급 | 판매 등록 시작 대비 활성화 완료율 | 60% 이상 |
| 탐색 | 검색 결과에서 앨범 상세 진입률 | 기준선 수집 후 목표 확정 |
| 구매 | 결제 시도 대비 PG 결제 성공률 | 사용자 이탈 제외 95% 이상 |
| 이행 | 결제 후 96시간 내 택배사 집화 완료율 | 90% 이상 |
| 신뢰 | 분쟁 없이 완료된 거래 비율 | 97% 이상 |
| 운영 | 분쟁 없는 주문의 배송 완료부터 거래 완료까지 중앙값 | 72시간 이하 |
| 무결성 | 이중 판매 건수 | 0건 |
| 무결성 | 미조정 결제·환불·정산 건수 | 0건 |

초기 목표는 가설이며 베타 4주 데이터로 재설정한다. 지표 개선을 위해 안전 정책을 완화해서는 안 된다.

## 3. 사용자와 핵심 과업

### 3.1 구매자

- 정확한 앨범·판본을 찾고 싶다.
- 여러 판매글의 가격, 상태, 구성품, 판매자 신뢰 정보를 비교하고 싶다.
- 안전하게 결제하고 배송 과정을 확인하고 싶다.
- 상품에 문제가 있으면 정산 전에 증빙을 제출하고 해결받고 싶다.

### 3.2 판매자

- 공용 카탈로그를 이용해 상품을 빠르게 등록하고 싶다.
- 상태와 구성품을 명확히 고지해 불필요한 분쟁을 줄이고 싶다.
- 발송 기한과 예상 정산액·정산 시점을 알고 싶다.

### 3.3 운영자·고객지원 담당자

- 중복되거나 잘못된 앨범 카탈로그를 검수·병합하고 싶다.
- 신고 상품의 신규 거래를 즉시 중단하고 싶다.
- 주문 당시 정보와 양측 증빙을 바탕으로 분쟁을 판정하고 싶다.
- 환불·정산 실패를 재처리하고 모든 변경의 행위자와 사유를 확인하고 싶다.

## 4. 범위와 우선순위

### 4.1 P0: MVP 필수 범위

- 회원가입, 로그인, 연락처 인증, 주소, 판매자 정산 정보
- 앨범 카탈로그 검색·필터·상세·신규 앨범 제안
- 실제 상품 판매 등록·수정·철회·상태 관리
- 판매글 비교와 고정가 즉시 구매
- 체크아웃, PG 결제, 결제 실패·만료 복구, 전액 환불
- 배송정보 등록·조회, 구매 확정, 자동 확정, 판매대금 정산
- 취소, 분쟁 접수, 반품, 정산 보류
- 거래 상태 타임라인과 이메일 또는 앱 내 알림
- 신고, 판매글 차단, 사용자 제한, 카탈로그 검수, 분쟁·환불·정산 운영 도구
- 상태 변경 이력과 운영자 감사 로그

### 4.2 P1: MVP 안정화 후 검토

- 관심 앨범·판매글, 저장 검색, 재입고·가격 알림
- 여러 배송지 저장과 공개 판매자 평판
- 거래 완료 후 구매자·판매자 후기
- 최근 거래가와 가격 이력
- 가격 제안
- 판매자 일괄 등록과 묶음 배송
- 고급 검색, 오타 보정, 추천 정렬
- 사업자 판매자와 새 상품 판매

### 4.3 비범위

- 구매·판매 입찰, 경매, 자동 체결 호가창
- 자체 검수센터, 정품 감정, 창고·보관 판매
- 해외 배송, 다중 통화, 해외 정산
- 직거래, 현금 송금, 플랫폼 자체 지갑·포인트
- 실시간 채팅, 커뮤니티 피드, 팔로우
- 여러 판매자의 장바구니 또는 부분 환불
- 구독, 광고, 라이브 커머스
- 네이티브 모바일 앱

## 5. 핵심 개념과 정보 구조

### 5.1 도메인 용어

| 용어 | 정의 |
| --- | --- |
| 앨범(Album) | 제목, 아티스트 등 여러 판본이 공유하는 작품 단위 |
| 판본(Edition) | 매체, 발매국·연도, 레이블, 카탈로그 번호, 바코드, 색상·한정판 속성으로 구분되는 공용 카탈로그 단위 |
| 판매글(Listing) | 판매자가 실제 보유한 실물 한 개의 사진, 상태, 구성품, 하자, 가격을 담은 거래 단위 |
| 주문(Order) | 구매자와 판매자, 결제액, 배송지, 판매글 스냅샷 및 거래 기한을 고정한 기록 |
| 구매 확정 | 구매자가 수령 상품에 문제가 없음을 확인하거나 72시간의 문제 제기 기간이 만료된 상태 |
| 분쟁(Dispute) | 상품·배송 문제로 자동 완료와 정산을 멈추고 운영 판단을 요청한 상태 |
| 정산(Settlement) | 거래 완료 후 PG 또는 정산 사업자를 통해 판매자에게 대금을 지급하는 과정 |

### 5.2 앨범 카탈로그와 판매글 분리

공용 판본에는 다음 정보를 저장한다.

- 아티스트, 앨범명, 매체(LP/CD/Cassette/기타 허용값)
- 버전·에디션명, 발매국, 발매 연도 또는 발매일
- 레이블, 카탈로그 번호, 바코드
- LP 색상·크기·회전수 등 판본 식별에 필요한 선택 속성
- 대표 이미지와 출처·사용 권한 정보

개별 판매글에는 다음 정보를 저장한다.

- 실제 상품 사진
- 개봉 여부, 미디어 상태와 패키지 상태. 미개봉이면 미디어 상태는 `미확인`
- 구성품 포함·누락 여부
- 스크래치, 변색, 찢김, 소음 등 하자 설명
- 미개봉 여부, 구매 가격, 배송비·수수료, 예상 정산액

검색 결과는 판본 카드에 활성 판매글의 최저가와 개수를 표시하고, 판본 상세에서 개별 판매글을 비교하게 한다. 필터가 적용되면 하나 이상의 활성 판매글이 모든 조건과 일치하는 판본만 노출하며 최저가와 개수도 그 일치 집합에서 계산한다. 예약·거래 중·판매 완료·차단 상태는 최저가와 재고 수에서 제외한다.

### 5.3 주요 화면

1. 홈·통합 검색
2. 검색 결과·필터
3. 앨범/판본 상세와 활성 판매글 목록
4. 판매글 상세
5. 신규 앨범 제안
6. 판매 등록·미리보기
7. 체크아웃·결제 결과
8. 구매·판매 내역과 주문 상세 타임라인
9. 분쟁 접수·증빙 제출
10. 프로필·주소·정산 정보
11. 운영자 카탈로그·신고·주문·분쟁·환불·정산 화면

## 6. 핵심 사용자 흐름

### 6.1 구매 흐름

1. 사용자가 제목, 아티스트, 카탈로그 번호 또는 바코드로 검색한다.
2. 매체, 상태, 가격, 판매 가능 여부로 좁힌다.
3. 판본 상세에서 개별 판매글의 상태, 사진, 구성품, 총 결제 예상액을 비교한다.
4. 구매할 판매글을 선택한다.
5. 로그인·연락처 인증과 배송지를 확인한다.
6. 서버가 판매 가능 여부와 가격을 다시 확인하고 판매글을 10분간 원자적으로 점유한다.
7. 사용자가 상품가, 배송비, 수수료, 총액과 취소·분쟁 정책에 동의하고 PG 결제를 완료한다.
8. 판매자가 72시간 안에 유효 운송장을 등록하고 결제 후 96시간 안에 택배사 집화를 완료한다.
9. 구매자는 배송 타임라인을 확인하고 수령 후 구매 확정하거나 72시간 안에 분쟁을 접수한다.
10. 구매 확정 시 거래가 완료되고 판매자 정산이 시작된다.

### 6.2 판매 흐름

1. 판매자가 판매할 앨범을 검색한다.
2. 정확한 판본을 선택한다. 없으면 필수 식별 정보를 입력해 신규 앨범을 제안한다.
3. 신규 제안은 운영자 승인 전까지 `검토 대기`이며 연결된 판매글은 초안으로 보존한다.
4. 판매자는 실제 사진, 상태, 구성품, 하자, 가격을 입력한다.
5. 활성화 직전 구매자 결제 예상액과 판매자 예상 정산액을 확인하고 판매 정책에 동의한다.
6. 판매글이 활성화되면 수정·철회할 수 있지만 구매자가 점유한 이후 핵심 정보는 잠긴다.
7. 결제 완료 알림을 받으면 72시간 안에 운송장을 등록하고, 결제 후 96시간 안에 택배사 집화가 확인되도록 발송한다.
8. 구매 확정 후 정산 상태를 추적한다.

### 6.3 분쟁 흐름

1. 구매자는 배송이 `EXCEPTION`이면 미배송·분실 사유와 가능한 배송 증빙을, 배송 완료 후에는 72시간 안에 상품 문제 사유·설명·사진을 제출한다.
2. 접수 즉시 자동 구매 확정 타이머와 판매자 정산을 중단한다.
3. 운영자는 주문 당시 판매글 스냅샷, 배송 이벤트, 양측 증빙과 상태 이력을 확인한다.
4. 운영자는 `구매자 인용`, `판매자 인용`, `추가 자료 요청`, `반품 필요` 중 하나를 결정한다.
5. 반품이 필요하면 추적 가능한 반품 배송 완료 후 원결제 수단으로 전액 환불한다. 운영자가 반품 면제를 명시한 경우에만 반품 없이 환불한다.
6. 판매자 인용이면 거래를 완료하고 정산을 재개한다.

| ADM-003 | P0 | 금전·계정·거래 상태를 바꾸는 운영 작업에는 사유가 필수이며 행위자, 시각, 변경 전후 값을 기록한다. |

## 8. 상태 모델과 전이 규칙

거래의 사용자용 타임라인은 하나로 보여주되, 시스템은 판매글, 주문, 결제, 배송, 분쟁, 정산을 독립된 상태축으로 저장한다.

### 8.1 카탈로그 제안과 판매글 상태

신규 판본 검토는 판매글 상태와 분리한다.

```text
CatalogProposal: PENDING → APPROVED
                         → REJECTED → PENDING(수정 후 재제출)
                         → MERGED
```

연결된 판매글은 제안이 `APPROVED` 또는 `MERGED`가 될 때까지 `DRAFT`로 유지한다. `MERGED`이면 운영자가 선택한 기존 판본으로 연결을 옮기고, `REJECTED`이면 사유를 표시한다.

```text
DRAFT → ACTIVE → CHECKOUT_RESERVED → IN_TRANSACTION → SOLD
  │         │              └── 결제 실패/만료 ─────────→ ACTIVE
  │         └→ WITHDRAWN
  └→ WITHDRAWN

IN_TRANSACTION ── 구매자 정상 취소 + REFUNDED ──→ ACTIVE
IN_TRANSACTION ── 판매자 귀책 + REFUNDED ───────→ WITHDRAWN
IN_TRANSACTION ── 구매자 분쟁 인용 + REFUNDED ──→ BLOCKED
ACTIVE/CHECKOUT_RESERVED ── 운영 차단 ──────────→ BLOCKED
```

| 상태 | 설명 |
| --- | --- |
| `DRAFT` | 필수 정보 입력 전이거나 연결된 판본이 승인되지 않은 초안 |
| `ACTIVE` | 검색·상세에 노출되고 구매 가능한 상태 |
| `CHECKOUT_RESERVED` | 한 구매자가 10분 동안 결제를 진행하는 상태 |
| `IN_TRANSACTION` | 결제 완료 후 거래 진행 중인 상태 |
| `SOLD` | 거래가 완료된 종결 상태 |
| `WITHDRAWN` | 판매자가 구매 전 철회했거나 판매자 귀책으로 종료된 상태 |
| `BLOCKED` | 정책 위반·구매자 인용 분쟁 또는 운영 검토로 재판매가 금지된 상태 |

### 8.2 주문 상태

```text
PAYMENT_PENDING
  → AWAITING_SHIPMENT
  → SHIPPED                 (택배사 PICKED_UP)
  → CONFIRMATION_PENDING    (택배사 DELIVERED)
  → COMPLETED

PAYMENT_PENDING → CANCELED
AWAITING_SHIPMENT / SHIPPED / CONFIRMATION_PENDING
  → CANCEL_PENDING
  → CANCELED
```

주문 상태는 사용자가 이해할 큰 단계만 나타낸다. 운송장 등록(`LABEL_REGISTERED`)만으로는 `AWAITING_SHIPMENT`를 벗어나지 않고 택배사 집화(`PICKED_UP`)에서 `SHIPPED`, 배송 완료(`DELIVERED`)에서 `CONFIRMATION_PENDING`으로 전이한다. `CONFIRMATION_PENDING` 중 분쟁이 접수되면 주문 진행은 유지하되 분쟁 상태가 `OPEN`이 되고 자동 완료가 중단된다. 결제된 주문은 PG 환불 성공을 확인한 뒤에만 `CANCELED`가 된다.

### 8.3 독립 상태축

- 결제: `READY → PAID → REFUND_PENDING → REFUNDED`, 승인 실패 시 `FAILED`
- 배송: `NONE → LABEL_REGISTERED → PICKED_UP → IN_TRANSIT → DELIVERED`, 예외 시 `EXCEPTION`
- 분쟁: `NONE → OPEN ↔ EVIDENCE_REQUESTED`; 이후 `RESOLVED_SELLER`, `RESOLVED_BUYER` 또는 `RETURN_REQUIRED → RETURN_IN_TRANSIT → RETURN_DELIVERED → RESOLVED_BUYER`
- 정산: `ON_HOLD → READY → PROCESSING → PAID`, 실패 시 `FAILED`

### 8.4 분쟁 판정 결과

| 판정 | 주문·결제·판매글·정산 결과 |
| --- | --- |
| 추가 자료 요청 | 주문과 결제는 유지하고 자동 완료·정산을 계속 보류한다. |
| 판매자 인용 | 분쟁을 `RESOLVED_SELLER`, 주문을 `COMPLETED`, 판매글을 `SOLD`, 정산을 `READY`로 원자적으로 전환한다. |
| 구매자 인용·반품 면제 | 주문을 `CANCEL_PENDING`, 결제를 `REFUND_PENDING`, 판매글을 `BLOCKED`로 두고, 환불 성공 후 주문을 `CANCELED`, 결제를 `REFUNDED`로 전환한다. |
| 구매자 인용·반품 필요 | 반품 배송이 `RETURN_DELIVERED`가 될 때까지 결제와 정산을 보류하고, 반품 확인 후 구매자 인용·반품 면제와 같은 환불 결과를 적용한다. |

판매자 수령 거부나 반품 배송 예외는 자동 환불하지 않고 운영 검토로 보낸다.

### 8.5 필수 불변조건

- 결제 성공을 서버에서 확인하기 전 배송 단계로 이동할 수 없다.
- 진행 중인 주문 하나만 판매글 하나를 점유할 수 있다.
- 결제 시점의 판매글 설명, 사진, 가격, 수수료, 배송지, 정책 버전을 주문에 스냅샷으로 보존한다.
- 분쟁 중에는 자동 구매 확정과 정산을 실행하지 않는다.
- 주문이 `COMPLETED`, 결제가 `PAID`, 분쟁이 `NONE` 또는 `RESOLVED_SELLER`일 때만 정산할 수 있다.
- 결제된 주문의 취소는 DB 상태만 바꾸지 않고 PG 환불 결과와 조정해야 한다.
- 구매자 취소는 택배사 집화 전까지만 자동 승인한다. 집화와 취소가 동시에 발생하면 조건부 갱신으로 정확히 하나만 성공해야 한다.
- 판매글은 PG 환불 성공 전에는 `IN_TRANSACTION`에서 `ACTIVE`, `WITHDRAWN`, `BLOCKED` 중 어느 상태로도 전환하지 않는다.
- 판매자 귀책 취소·발송 기한 초과 후에는 판매글을 자동 재활성화하지 않는다.
- 자동 구매 확정과 분쟁 접수가 동시에 발생하면 조건부 갱신으로 정확히 하나만 성공해야 한다.
- 환불과 정산은 같은 거래 금액에 동시에 성공할 수 없다.
- 기한 처리 작업을 재실행해도 주문, 환불, 정산, 알림이 중복 생성되지 않는다.

### 8.6 기본 기한

| 항목 | 기본값 | 만료 처리 |
| --- | --- | --- |
| 체크아웃 점유 | 10분 | 결제가 없으면 점유 해제 |
| 판매자 발송정보 등록 | 결제 완료 후 72시간 | 운영 검토, 증빙이 없으면 주문 취소·전액 환불 |

## 9. 핵심 인수 기준

### 9.1 검색과 상세

- Given 활성 판매글이 있는 판본, When 사용자가 제목·아티스트·카탈로그 번호·바코드를 검색, Then 정규화된 검색 결과에 해당 판본이 노출된다.
- 예약·거래 중·판매 완료·차단된 판매글은 판본 카드의 최저가와 재고 수에 포함되지 않는다.
- 상태·가격 필터가 적용되면 모든 조건과 일치하는 활성 판매글이 하나 이상인 판본만 노출하고 최저가·개수도 그 일치 집합에서 계산한다.
- 가격 범위의 최솟값·최댓값은 포함하며, 같은 정렬값에서는 판본 ID를 보조 키로 사용해 페이지 간 순서가 바뀌지 않는다.
- 같은 제목의 다른 매체·판본은 매체, 발매 정보, 카탈로그 번호로 구별된다.
- 결과 없음 화면에서 검색어 수정과 신규 앨범 제안을 시작할 수 있다.
- 신규 판본 제안이 승인되면 연결된 초안을 게시할 수 있고, 병합되면 기존 판본으로 이동하며, 거절되면 사유를 확인하고 수정·재제출할 수 있다.
- 페이지를 이동하거나 추가 로드해도 같은 판매글이 중복 노출되지 않는다.

### 9.2 판매 등록

- 필수 사진 1장, 상태, 구성품, 하자, 가격 중 하나라도 없으면 판매글을 활성화할 수 없다.
- 미개봉 상품은 미디어 상태를 `미확인`으로 저장하고 봉인 상태·외부 패키지·카탈로그 번호 사진과 내부 구성품 미확인 고지가 없으면 활성화할 수 없다.
- 개봉 상품은 미디어/라벨 사진과 미디어·패키지 상태를 각각 입력해야 한다.
- 판매 등록 미리보기와 공개 상세의 핵심 정보가 일치한다.
- 점유 이후 핵심 정보 수정·삭제 요청은 거절되고 진행 중 거래로 안내된다.
- 신규 판본이 중복 판본에 병합돼도 판매글 초안이 올바른 판본으로 이동한다.

### 9.3 동시 구매와 결제

- 두 사용자가 같은 판매글을 동시에 구매해도 한 명만 점유·결제할 수 있다.
- 결제 실패나 점유 만료 후 판매글이 다시 `ACTIVE`가 된다.
- 브라우저 성공 화면만 도착하고 검증된 PG 웹훅이 없으면 주문을 결제 완료로 표시하지 않는다.
- 검증된 PG 웹훅이라도 상점 주문 ID, 정수 KRW 금액, 통화, 상태가 서버 견적과 하나라도 다르면 `PAID`로 전이하지 않고 운영 경고와 취소·환불 작업을 만든다.
- 같은 웹훅을 여러 번 수신하거나 역순으로 수신해도 주문·결제·환불은 한 번만 처리된다.
- 점유 만료 후 결제 성공 웹훅이 도착하면 다른 구매를 침범하지 않고 해당 결제를 환불 대기로 전환한다.

### 9.4 배송과 완료

- 유효하지 않거나 진행 거래에서 재사용된 운송장을 정상 발송으로 표시하지 않는다.
- 운송장 입력만으로 주문을 `SHIPPED`로 바꾸지 않고 택배사 `PICKED_UP` 이벤트에서만 전이한다.
- 결제 후 96시간 안에 집화가 없으면 자동 완료·정산을 중단하고 운영 검토를 생성한다.
- 택배사 예외 이벤트가 오거나 집화 후 7일 안에 배송 완료가 없으면 배송을 `EXCEPTION`으로 전환하고 미배송·분실 분쟁을 열 수 있다.
- 배송 완료 전 구매 확정과 자동 완료는 실행되지 않는다.
- 배송 완료 후 구매자가 확정하면 즉시 거래가 완료되고 정산 대기가 생성된다.
- 72시간 동안 분쟁이 없으면 한 번만 자동 완료·정산 요청·알림이 실행된다.

### 9.5 취소, 분쟁과 환불

- 구매자가 택배사 집화 전에 취소하면 전액 환불하고, 환불 성공 후 판매자 계정·상품에 제한이 없을 때만 판매글을 다시 활성화한다.
- 집화 이벤트와 구매자 취소가 동시에 처리돼도 정확히 하나만 성공한다.
- 판매자 취소나 발송 기한 만료이면 구매자 전액 환불을 시작하고 판매글을 임의로 재활성화하지 않는다.
- 분쟁 접수 즉시 자동 완료 타이머와 정산 작업이 멈춘다.
- 자동 구매 확정과 분쟁 접수가 동시에 처리돼도 정확히 하나만 성공한다.
- 판매자 인용, 구매자 인용, 반품 필요 결과는 8.4의 주문·결제·판매글·정산 상태 묶음을 원자적으로 적용한다.
- 운영자는 주문 당시 사진·설명·금액, 배송 이력, 양측 증빙, 모든 상태 변경을 한 화면에서 확인할 수 있다.
- 반품 필요 판정은 반품 배송 완료 전 환불 완료로 표시되지 않는다.
- PG 환불 실패 시 결제 상태는 `REFUND_PENDING`을 유지하고 운영 경고가 생성된다.
- 모든 환불은 원결제 수단으로 처리한다.

### 9.6 권한과 운영

- 다른 사용자의 비공개 주문 URL을 직접 입력해도 주문이나 개인정보가 노출되지 않는다.
- 판매글 상세와 체크아웃에 자체 실물 검수를 제공하지 않는다는 고지와 플랫폼 보증 범위가 노출된다.
- 사용자가 판매글·사용자를 신고할 수 있고, 운영 차단 후에는 신규 점유와 결제가 불가능하다.
- 결제 점유 중 판매글이 차단되면 점유를 취소하고 차단 후 늦게 도착한 결제 성공은 환불한다.
- 판매자는 거래가 종료되면 주문 이력은 보더라도 구매자의 상세 배송지에 다시 접근할 수 없다.
- 차단된 판매글에서는 새로운 체크아웃을 시작할 수 없다.
- 운영자의 차단, 환불, 정산 보류, 분쟁 판정은 사유가 없으면 실행되지 않는다.
- 운영 작업의 행위자, 시각, 변경 전후 값이 수정 불가능한 감사 이벤트로 남는다.

## 11. 비기능 요구사항

### 11.1 성능과 가용성

- 검색 API는 정상 부하에서 p95 1초 이내, 일반 읽기 API는 p95 500ms 이내를 목표로 한다. 외부 PG·택배 응답 시간은 별도 측정한다.
- 모바일 4G 환경에서 주요 공개 화면의 LCP 2.5초 이내를 목표로 한다.
- 월 가용성 목표는 99.9%다. 결제·환불·정산 장애는 별도 경보한다.
- 목록은 커서 또는 안정적인 페이지네이션을 사용해 중복·누락을 방지한다.

### 11.2 보안과 개인정보

- 전 구간 TLS, 저장 데이터 암호화, 최소 권한, 관리자 다중 인증을 적용한다.
- 비밀번호는 검증된 단방향 해시로 저장하고 비밀값을 코드나 로그에 남기지 않는다.
- 결제정보는 PG 호스팅 또는 토큰화 화면을 사용한다.
- 주소, 연락처, 정산 정보는 로그와 분석 도구에서 마스킹한다.
- 로그인·검색·업로드·결제·신고 API에 속도 제한과 비정상 사용 탐지를 적용한다.
- 업로드 파일의 MIME, 확장자, 크기, 악성 콘텐츠를 검사하고 공개 저장소와 원본 저장소를 분리한다.
- OWASP Top 10과 권한 우회 시나리오를 출시 전 점검한다.

### 11.3 정합성과 복구

- 모든 KRW 금액은 부동소수점이 아닌 정수로 저장·계산하고 주문 견적을 결제 전에 고정한다.
- 판매글 점유는 원자적 연산 또는 동등한 동시성 제어를 사용한다.
- 외부 이벤트는 서명 검증, 멱등 처리, 재시도, 실패 대기열을 지원한다.
- 결제·환불·정산 외부 원장과 내부 상태를 주기적으로 대사한다.
- 주요 상태 변경과 운영 명령은 상관관계 ID를 포함한 구조화 로그와 지표를 남긴다.
- 백업 복구 절차를 문서화하고 출시 전에 실제 복구 훈련을 수행한다.

### 11.4 사용성과 접근성

- 모든 핵심 흐름을 키보드로 수행할 수 있고 입력 필드에 레이블·오류 설명을 제공한다.
- 상태는 색상만으로 구분하지 않고 텍스트와 아이콘을 함께 사용한다.
- 이미지에는 대체 텍스트를 제공하고 사용자 업로드 이미지의 핵심 정보를 설명 필드로 보완한다.
- 사용자가 오류 후 입력 내용을 잃지 않고 재시도할 수 있어야 한다.

## 12. 분석 이벤트

다음 이벤트에는 `user_id`의 비식별 키, `edition_id`, `listing_id`, `order_id`, 발생 시각, 진입 경로를 필요한 범위에서 포함한다. 개인정보와 자유 입력 원문은 분석 속성에 넣지 않는다.

- `search_submitted`, `search_result_clicked`, `filter_applied`
- `catalog_proposal_started`, `catalog_proposal_submitted`, `catalog_proposal_approved`
- `listing_started`, `listing_validation_failed`, `listing_published`, `listing_withdrawn`
- `checkout_started`, `listing_reserved`, `reservation_expired`
- `payment_succeeded`, `payment_failed`, `late_payment_detected`
- `shipment_registered`, `shipment_picked_up`, `delivery_completed`
- `purchase_confirmed`, `purchase_auto_confirmed`, `transaction_completed`
- `cancel_requested`, `refund_requested`, `refund_succeeded`, `refund_failed`
- `dispute_opened`, `dispute_resolved`
- `settlement_requested`, `settlement_succeeded`, `settlement_failed`
- `listing_reported`, `listing_blocked`

퍼널은 검색 → 상세 → 체크아웃 → 결제 → 발송 → 거래 완료 단계로 본다. 실패율은 사용자 이탈, 정책 차단, 외부 사업자 오류를 분리한다.

## 13. 구현과 출시 계획

저장소 개발 원칙에 따라 각 증분은 작동하는 세로 흐름으로 구현하고, 다음 단계 전에 자동 테스트와 수동 시나리오를 통과시킨다.

### Increment 1: 내부 종단 프로토타입

- 인증 최소 기능
- 사전 등록된 소수 앨범 검색과 상세
- 판매 등록과 고정가 구매
- 모의 결제
- 주문 상태 타임라인

완료 조건: 한 명의 판매자와 구매자가 검색 → 등록 → 구매 → 발송 → 구매 확정 흐름을 끝까지 수행한다.

### Increment 2: 실제 결제 안전성

- PG 샌드박스 결제·전액 환불
- 원자적 판매글 점유
- 웹훅 서명 검증·멱등성·재시도
- 결제 대사와 운영 경고

완료 조건: 동시 구매, 중복·역순·지연 웹훅, 결제 실패·만료 테스트를 통과하고 이중 판매가 0건이다.

### Increment 3: 배송과 지연 정산

- 운송장 검증과 택배 추적
- 구매 확정·72시간 자동 확정
- 정산 보류·요청·실패 복구
- 거래 알림

완료 조건: 배송 이벤트 장애와 기한 작업 재실행에도 중복 완료·정산·알림이 없다.

### Increment 4: 최소 분쟁·운영 도구

- 분쟁·증빙·반품·전액 환불
- 신고·차단·사용자 제한
- 주문 스냅샷과 감사 로그
- 운영자 역할·권한

완료 조건: 대표 분쟁 시나리오를 운영자가 처음부터 끝까지 처리하고 모든 금전·상태 변경을 추적할 수 있다.

### Increment 5: 카탈로그 확장과 Closed Beta

- 신규 앨범 제안·중복 병합
- 상태·구성품 가이드 보정
- 지표 대시보드
- 제한된 판매자·구매자 대상 베타

완료 조건: P0 인수 기준, 운영 매뉴얼, 정책·법률·PG 출시 게이트를 모두 통과한다.

### KREAM

[KREAM 구매 단계](https://kream.co.kr/faq/247), [판매 단계](https://kream.co.kr/faq/255), [LP/CD 상품 예시](https://kream.co.kr/products/585755)는 공용 상품 카탈로그에서 옵션을 고른 뒤 구매·판매를 시작하고, 거래 단계와 기한을 공개하며, 조건을 충족한 거래만 정산하는 패턴을 제공한다. VYNL은 다음만 채택한다.

- 공용 앨범·판본 카탈로그에서 구매·판매를 시작하는 구조
- 가격 정보와 명확한 거래 단계
- 기한이 있는 단계별 상태와 조건부 정산
- 정책 위반과 거래 실패를 상태·이력으로 관리하는 방식

KREAM의 일반 거래는 익명 호가와 플랫폼 검수를 중심으로 하므로, 실제 개별 실물의 사진·상태·구성품을 비교하는 판매글 구조는 VYNL의 앨범 거래 특성에 맞춘 별도 설계다.

중앙 검수센터, 보관 판매, 구매·판매 입찰, 정품 보상은 운영 비용과 전문성이 큰 별도 사업 모델이므로 MVP에 포함하지 않는다.

### 4mation

[레사모(4mation) 검색](https://4mation.net/search?v=%EC%8A%A4%ED%8E%98%EC%9D%B8)과 [시세 아카이브](https://4mation.net/kit-archive?team=Real+Madrid&type=training)는 축구용품 마켓의 상품군별 거래, 팀·시즌·유형별 탐색, 시세 정보와 커뮤니티를 한 서비스에 구성한 사례다. VYNL은 카테고리 고유 속성에 맞춘 탐색·판매 정보 구조를 참고하되, 커뮤니티 기능은 거래 안전성과 유동성을 검증한 뒤 검토한다.

### 적용 원칙

레퍼런스의 화면이나 정책을 그대로 복제하지 않는다. 관찰 가능한 문제 해결 패턴만 가져오고, VYNL의 앨범 판본·상태·구성품 특성과 MVP 운영 역량에 맞게 단순화한다.
